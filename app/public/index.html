01 / CONTAINER
◇

Image vs. container

An image is a blueprint: immutable filesystem layers and startup metadata. A container is one isolated, running instance of that blueprint.

MENTAL MODEL

Dockerfile → image → container. Build produces a reusable artifact. Run adds a process, network identity, and temporary writable layer. Deleting a container does not delete its image.

IN THIS PROJECT

app/Dockerfile compiles TypeScript in a builder stage. The runtime stage copies only production files, listens on port 3000, and runs as the non-root node user.

IMAGE LAYERS & CACHE

Each Dockerfile instruction creates or reuses a content-addressed layer. Copying dependency manifests before application source lets Docker reuse the expensive install layer when only source code changes. A changed instruction invalidates that layer and every layer after it.

RUNTIME ISOLATION

A container is not a small virtual machine. It is a normal host process isolated with Linux namespaces and constrained with cgroups. It shares the host kernel, which makes startup fast, but its filesystem and network view appear separate.

DATA & FAILURE

The writable container layer is ephemeral: replacing the container loses changes stored there. Databases therefore mount a volume. Logs should go to stdout and configuration should enter through environment variables so the same image can run unchanged in each environment.

COMMON MISCONCEPTION

localhost inside a container means that same container—not your laptop and not another Compose service. Containers reach peers through network DNS names such as postgres; published ports are primarily how the host reaches a container.

02 / RELIABILITY
♡

Live is not ready

Liveness asks “restart me?” Readiness asks “send me traffic?” The two signals deliberately control different Kubernetes behaviors.

MENTAL MODEL

Alive + unready is a valid state. An unready pod stays running but leaves Service endpoints. A repeatedly non-live pod is restarted by the kubelet.

IN THIS PROJECT

/health/live proves Node.js responds. /health/ready also reports database availability. Probe timings and paths live in kubernetes/deployment.yaml.

PROBE LIFECYCLE

After the initial delay, the kubelet calls each configured endpoint on its own schedule. One failed check does not immediately act: failureThreshold controls how many consecutive failures are required. A later successful readiness check automatically returns the pod to traffic.

WHY TWO SIGNALS

Liveness detects a process that cannot recover, such as a deadlocked event loop. Readiness represents temporary inability to serve useful work, such as startup, draining, or dependency loss. Using one strict check for both can turn a recoverable outage into repeated restarts.

DEPENDENCY POLICY

Not every dependency belongs in every check. Liveness should usually avoid downstream services: restarting this API cannot repair PostgreSQL. Readiness may include a dependency only when the API truly cannot serve meaningful requests without it.

DEBUGGING SIGNALS

A restart count that keeps rising points toward liveness failures or process crashes. A running pod with Ready=False points toward readiness. kubectl describe pod shows probe failures and events; application logs explain what the endpoint observed.

03 / AUTOMATION
⌁

Infrastructure as code

Configuration describes the desired result. Terraform compares that intent with saved state and real infrastructure before proposing changes.

MENTAL MODEL

Configuration + state + live API → plan. Resource references form a graph, allowing Terraform to order work instead of relying on a hand-written command sequence.

IN THIS PROJECT

terraform/main.tf declares a namespace, ConfigMap, Deployment, and Service. providers.tf configures the adapter that translates them into Kubernetes API calls.

HOW PLAN IS CALCULATED

Terraform refreshes known resources from the provider, compares their current attributes with configuration and state, then classifies differences as create, update, replace, or destroy. The plan is a proposal; infrastructure changes only when it is applied.

WHAT STATE DOES

State binds a Terraform address such as kubernetes_deployment_v1.api to one real API object. It also stores provider-returned attributes needed for future comparisons. State is operational data, not a cache that can always be discarded safely.

DRIFT & OWNERSHIP

A manual cluster edit creates drift between configuration and reality. The next plan may reverse that edit because Terraform treats configuration as the declared owner. Emergency changes should be captured back in code once the incident is stable.

TEAM SAFETY

Production teams normally store state in a remote backend with locking, encryption, and version history. Locking prevents two applies from racing; restricted access matters because state can contain resource identifiers and sensitive values.

04 / NETWORKING
⇄

Names, ports, and services

A service name is a stable promise. Containers and pods are replaceable, so callers need DNS and virtual service endpoints rather than hard-coded process addresses.

MENTAL MODEL

Name → virtual endpoint → healthy backend. DNS answers where a service can be reached. A port identifies the listening application on that address. A proxy or Service chooses one currently healthy backend.

COMPOSE NETWORKING

Compose creates a private bridge network and DNS entries from service names. The API reaches postgres:5432; it must not use localhost, which would refer to the API container itself.

KUBERNETES NETWORKING

Each pod receives an address, but that address changes when the pod is replaced. A ClusterIP Service provides stable DNS and selects ready pods by label. Its port is client-facing; targetPort is where the container listens.

PORT PUBLISHING

3000:3000 maps host port 3000 to container port 3000. Publishing is required for host-to-container access, but containers on the same Compose network communicate directly through service names and container ports.

COMMON FAILURES

Connection refused usually means the address resolved but nothing accepted that port. A DNS error means the name could not resolve. A timeout may indicate filtering, an unreachable route, or a process too overloaded to respond.

DEBUGGING ORDER

Check from the caller’s point of view: resolve the name, verify the address, test the TCP port, send the application request, then inspect endpoints and server logs. Testing only from the server can hide network-boundary failures.

05 / DELIVERY
↻

Safe rollouts and rollback

A deployment changes capacity gradually. Kubernetes creates new pods, waits for readiness, and removes old pods while preserving the desired replica count.

MENTAL MODEL

Desired version + rollout policy + health signals. A Deployment controller continuously moves actual pods toward the declared template without requiring an operator to replace each instance manually.

ROLLING UPDATE

maxSurge limits extra new pods and maxUnavailable limits missing capacity. Their combination controls rollout speed, temporary resource use, and how much traffic capacity can be lost during change.

READINESS GATE

A new pod does not count as available until readiness succeeds. If the new version never becomes ready, the rollout stops progressing while old healthy replicas can remain in service, depending on the rollout settings.

IMMUTABLE VERSIONS

Use an immutable image digest or unique version tag for each build. Reusing a mutable tag such as latest makes it difficult to prove which bytes are running and can produce different results across nodes.

ROLLBACK REALITY

kubectl rollout undo restores a previous pod template, not external state. A backward-incompatible database migration may prevent old application code from working, so data changes need an explicit compatibility and recovery plan.

WHEN ROLLOUTS FAIL

Inspect Deployment conditions, ReplicaSets, pod events, readiness output, and logs. Common causes include missing configuration, invalid image credentials, insufficient cluster capacity, and a startup path that exceeds probe timing.

06 / OBSERVABILITY
⌁

Logs, metrics, and traces

Observability explains unknown failures. Logs preserve events, metrics summarize behavior over time, and traces connect work across service boundaries.

THREE SIGNALS

Logs answer “what happened here?” Metrics answer “how is the system behaving overall?” Traces answer “where did this request spend time?” They overlap, but each supports a different investigation scale.

IN THIS PROJECT

GET /metrics exposes request duration, incident count, and service count as JSON. It demonstrates the signal, though production scrapers commonly expect a standard exposition format such as Prometheus text.

USEFUL METRICS

Start with request rate, error rate, and duration. Add saturation signals for constrained resources such as CPU, memory, connection pools, and queues. Prefer measurements that describe user-visible behavior over counts that merely look busy.

STRUCTURED LOGS

Machine-readable logs use consistent fields such as timestamp, level, service, request ID, route, and outcome. Write them to stdout so the runtime can collect them. Never log passwords, tokens, or unnecessary personal data.

CARDINALITY

A metric label creates a new time series for every distinct value. Bounded labels such as method or route are useful; unbounded values such as user ID or raw URL can create millions of series and overwhelm monitoring storage.

FROM SLI TO ALERT

An SLI is a measured behavior such as successful-request ratio. An SLO is its target over a window. Good alerts warn when error-budget consumption threatens the SLO and include enough context for an operator to choose an action.
